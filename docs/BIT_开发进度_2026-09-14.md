## 本轮完成

UpdateValidator、UnjailValidator 和 RotateConsensusKey 已完成从规范 CBOR、结构校验、费用分类、角色授权、当前状态解析、状态转换、供应会计、JMT 持久化到 ABCI 调度的完整执行链。空 Update、落后 sequence、错误 operator、新共识键缺少 PoP 或重复使用历史/待生效密钥都会在写状态前拒绝。

验证人记录升级为 v3。公开资料立即更新；佣金降低排到下个 epoch，佣金上调每次最多 100 bps，并同时执行 604800 链秒与 120960 块通知期。停用在集合选择生效，重新启用回到 Candidate。Unjail 同时执行 7200 链秒与 1440 块等待。共识密钥轮换排到下个 epoch，生效时才替换当前密钥，并为旧密钥记录证据责任结束高度和时间；当前、历史、待生效密钥执行全局唯一约束。

状态先升级到 v8 并新增 `meta/block_time_seconds`，随后因逐验证人累计佣金升级到 v9。PrepareProposal、ProcessProposal 和 FinalizeBlock 从 ABCI v0.38 Timestamp 取 Unix 秒，状态提交与区块时间同批落盘并拒绝时间倒退。佣金、jail 和密钥历史因此只依赖共识链时间，不读取节点本地墙钟。

状态进一步升级到 v10：staking parameters v3 固定 10000 次机会与 9500 bps 阈值，validator v5 以压缩 bit 窗口持久化实际签名机会、签名计数、epoch 编号和累计 score。只有 Commit flag 按请求中的实际 power 加分；Nil/Absent 只形成未签机会，完整窗口低于阈值时 jail 并输出 power=0。

真实 Groth16 集成用例扩展为 RegisterValidator、Delegate、UpdateValidator、UnjailValidator、RotateConsensusKey 和 ClaimCommission 六类 enabled staking envelope；每类都执行 Spend/Output 证明、授权、binding、费用、状态落盘、供应守恒和重启恢复。直接状态测试另覆盖同块连续 sequence、失败原子性、待生效变更与时间倒退。

epoch 奖励已按 `score_v / total_score` 用 U256 中间乘法分配当时全部 F，再按验证人已生效佣金率拆入旧池 P 与 operator 累计佣金 C。两层取整余数保留在协议容器，池的 `last_settled_epoch` 单调推进。结算、发行/放弃、P/C/F 变更和 staking 记录在同一候选事务验证；ClaimCommission 通过公开 release 把 C 转回 Q，并把 fee 计入 F。

ABCI PrepareProposal、ProcessProposal 和 FinalizeBlock 现在分别严格解析 local/proposed/decided last commit，并调用同一系统阶段。新 epoch 首块先计入上一块机会，再自动执行 score 消费、发行/奖励、pending 激活、计划变更和集合选择；FinalizeBlock 把 key/power 差异编码为 Ed25519 ValidatorUpdates，移除或轮换旧键时返回 power=0。

状态升级到 schema v11，新增版本化 `staking/effective_schedule`。已提交高度 H 保存 H/H+1/H+2 的精确实际验证者集合；集合按 CometBFT 的 power/地址规则规范排序并用固定 Tendermint 实现计算哈希。PrepareProposal、ProcessProposal 和 FinalizeBlock 现在要求 32 字节 `next_validators_hash` 精确匹配 H+1，H>1 的 last commit 则逐项匹配 H-1 的地址、power 和顺序。H 返回的 ValidatorUpdates 只更新 H+2，Commit 和重启都会交叉验证质押逻辑集合与 H+2 集合。

最后有效验证者保护已经接入。如果 downtime jail 或集合选择会把非空实际集合变为空，共识系统阶段返回 `HALT_NO_SAFE_VALIDATOR_SET`。系统阶段任一错误都会回滚供应、质押、触及索引和集合日程的内存变更，Prepare 还有第二层集合一致性检查。

新增真实应用四节点集成探针。四个由 CometBFT Go module v0.38.23 构建的进程分别连接四个 `bit-app`，每个应用使用独立 JMT/RocksDB；实测 H=6 的奖励后 ValidatorUpdates 到 H=8 才生效，应用从高度 10 的 durable 状态重启后追块，四节点固定高度 app hash 一致，ABCI Query 返回 ICS23 proof。停止一半投票权后链停止，恢复第三个节点后继续出块。该探针使用五块 epoch 和临时域分离摘要，边界在报告中明确记录。

状态升级到 schema v12，新增逐验证人的 `staking/candidates/<validator_id>` 排序记录。池奖励、pending 激活、停用/恢复和 jail/unjail 都在同一候选事务中删除旧排名并写入新排名；集合选择直接遍历按 stake 降序、validator_id 升序的索引前 64 项。创世、区块提交和重启恢复都严格核对索引，持久化 pool 被篡改但索引未同步时会拒绝打开。
